1.一个 session 连续聊了 200 轮，context 快爆了。你会怎么做压缩？如何确保压缩后的对话仍然流畅？
	这个问题有点复杂，就是压缩吧方案有很多，做优先级截断或者滑动摘要生成，的确是压缩了，但流畅就只限于保持主题逻辑上的连贯性，失去了一些细节，并且对于200轮这个数量级来说，摘要意思偏离加上一些之前的约束也会悄悄消失。而且如果这200轮是一个长任务的话，很容易丢失自己原本的目标或者偏离方向，总而言之这其实是一个综合性问题。所以我的做法是原始消息和工具结果都保留，作为事实源，依据事实层再派生最近对话、任务状态、情景摘要和检索索引。每一轮根据当前在做什么来取：长任务优先看目标、约束、进度和下一步；闲聊就看最近原文和以前聊过的事；追问旧细节时，先用摘要找线索，再回原文核对。摘要可以丢细节，但事实不能丢，关键回答要能追到来源。这样就能流畅的同时保证更高的准确率。

2.和聊天 Agent 熟悉半个月后，用户问了一个以前问过的问题。Agent 如何做 memory 召回更合理？
	合理的 memory 召回，关键在于把当时那次问答完整找回来，而不只是找最像的句子。把问题改写成能检索的问题，然后用语义、关键词、人物、项目和时间做混合召回。不要只找答案，而要把问题、背景、约束、回答和用户后续反馈作为一段情景一起取出来。若有多个相似候选，先澄清，不要硬猜。命中后核对来源、时间和事实是否过时，再决定是沿用上次结论、说明变化，还是重新回答。找不到就承认找不到，而且只在该用户自己的记忆范围内检索。

3.对于长程任务，大模型执行一段时间可能会忘掉目标，你知道哪些解决方案，有什么优缺？
	忘记目标有几种原因，有可能是对话太长了，目标被挤出上下文，也有可能目标还在，但注意力被当前步骤带走。或者是错误累积，前面一步偏了，后面越做越远等原因。针对这些，我知道的两个做法一个是多 Agent 分工。​ 主 Agent 只守最终目标、硬约束和验收标准，把任务拆开交给子 Agent，子 Agent 在干净的上下文里执行，只回传结果和证据。优点是每个 Agent 的上下文都短，目标不容易被过程稀释，能并行，某块失败也只重跑局部；缺点是交接时隐性约束容易丢，子 Agent 容易局部最优、不管整体，错误会在汇总时被放大。
	另一个是维护任务列表。​ 把目标、约束、已完成、进行中、下一步、阻塞项放在模型上下文之外，每轮重新注入，完成一项更新一项。优点是便宜、稳定、可以人工查看、重启后也能接着做；缺点是它只记“要做什么”不管“做得对不对”，模型能把没做的事标成完成，而且列表靠模型自己更新就会失真，它防的是忘进度，防不了理解错目标。

4.Agent 工具有同步和异步两类。异步工具不能让用户一直等，但结果依然重要。你会如何设计异步工具执行和完成通知？
	以异步测试为例子，核心是把测试当成一个有状态的任务，而不是一个会阻塞的函数。调用时不等结果，立刻返回一个 task_id 和 running 状态，但是一次 tool_use 必须对应一次 tool_result，这条返回就把本轮关掉，同时约定结果稍后以事件送达，否则之后拿同一个 id 补结果会冲突。任务本身落库，日志流式写文件、库里只留游标，配上心跳和超时，避免进程一挂任务永远卡在 running。跑完之后不让 worker 直接调模型，而是产生一个完成事件进 session 的事件循环。空闲就唤醒起一轮新推理，用户正在说话就排队，任务被取消就标成 stale 不注入。模型看到的是一条带 task_id、明确标为系统事件的结构化结果，结果只给结论、通过失败数和失败用例的错误栈，完整日志给引用让模型按需读，不然上千行输出会把之前的上下文挤掉。还要分清“测试挂了”和“工具执行失败”，退出码非 0 应该返回成功加失败详情，不然模型会去修工具而不是修代码。等待期间用户问“跑完了吗”，要有接口能查当前状态和输出尾部，也要能真的取消。总体上，调用完立刻还权、结果可靠送达、日志不污染上下文，就这三点。

5.Claude Code 的工具输出方式和国内 GLM / 豆包等 OpenAI-compatible function calling 有什么不同？他们各自这样设计的优缺点是什么？
	Claude把工具调用和结果作为消息content中的tool_use或者tool_result内容块管理，优势就是不需要额外的字符串解析和容错，对编码Agent中大量文件操作和结构化数据交换的场景尤其友好。而且在Agent SDK层提供结构化的tool_use_result，能承载资源链接、结构化内容、子智能体产出等元数据，因此更适合深度编排的编码 Agent，复杂协作灵活。还有超大工具返回结果的持久化与显式省略，维护系统稳定性。缺点就是生态锁定明显、与OpenAI协议不兼容、切换非Claude模型时可能丢失cache_control等缓存能力且CLI流式输出对部分工具输出支持有限。GLM和豆包则主要遵循OpenAI的协议，模型以独立的tool_calls数组或 function_call对象返回函数名和 JSON 参数，工具结果再作为role: "tool"`消息回传，豆包在部分场景还可能用XML标签或文本标记触发，优点是通用性和互操作性强、实现调试简单并且OpenAI生态丰富。缺点是复杂 Agent 编排灵活性稍逊，且不同厂商在并行调用、嵌套 schema 等边缘场景可能存在细微格式差异，需要额外容错测试。
