# 设计说明

写代码之前先定下来的东西：做什么、不做什么、怎么算做完。

---

## 一、目标与非目标

**目标**

1. 不依赖任何 agent 框架，从零实现一个能跑起来的 Agent：接收输入 → 调模型 → 解析输出 → 调工具 → 回注结果 → 直到给出答案。
2. 至少 3 个工具，其中一个必须是待办；工具通过 schema 注册，由模型自主决定调不调、怎么调。
3. 会话可隔离、可续聊；同一个进程里能同时服务多个独立会话。
4. 上下文超长时能自己处理，不把错误抛给用户。
5. 出问题时能复盘：每轮发生了什么要能查到。

**非目标**

- 不做多机部署、不做权限体系、不做计费。
- 不做流式输出（一次请求返回完整结果）。
- 不接向量库；检索先用关键词。

非目标不是"以后也不做"，而是这一版不把复杂度花在上面。

## 二、技术栈

| 选择 | 理由 |
|---|---|
| Python 3.10+ | 类型标注够用，生态成熟；不引额外类型库 |
| 原生 `http` / `httpx` 调模型接口 | 不用 SDK，避免"框架替我们做了决策"而说不清细节 |
| FastAPI + 原生 JS 单页 | 只做接口和展示，不引前端构建链 |
| JSON 文件存储 | 会话量小，可读、可 grep、可手工修；换数据库时接口不变 |
| pytest | 离线、确定、毫秒级 |
| 不引 agent 框架 | 题目要求；也便于逐个环节讲清做了什么 |

## 三、模块划分

| 模块 | 职责 | 不负责 |
|---|---|---|
| `core/loop.py` | 一轮的主流程：装配 → 调模型 → 解析 → 执行工具 → 落库 | 不决定"发什么内容"（交给 context） |
| `core/context.py` | 决定每次发给模型的消息、何时压缩、压缩到什么程度 | 不调模型、不执行工具 |
| `core/llm.py` | 序列化请求、解析响应、重试 | 不判断业务语义 |
| `core/parser.py` | 把模型输出变成可执行决策，处理畸形参数 | 不决定接下来做什么 |
| `tools/` | 工具注册、schema 校验、超时、状态注入 | 不管理对话 |
| `session/` | 会话数据结构、存取、按会话发锁 | 不知道工具和模型的存在 |
| `core/trace.py` | 记录每轮事件 | 不影响主流程 |

一条边界：**工具只能读写传进来的会话状态，不能碰全局变量**。这是多会话隔离能成立的前提。

## 四、关键设计

### 4.1 一次请求的生命周期

```
加锁（按 session_id）
  → 取或建会话
  → 循环（上限 6 次模型调用）
      装配上下文 → 调模型 → 解析 → 分支（调工具 / 收尾）
  → 达上限则禁用工具再问一次
  → 落库 + 写 trace
  → 释放锁
```

### 4.2 上下文分层

固定系统提示、滚动摘要、状态快照放 system；最近若干轮原文放 messages。预算按全量历史判定，超了才压。

### 4.3 压缩分级

见 §4.4；原则是"能改表示就不改结构，能留意图就不留细节"。

### 4.4 记忆分层

上下文里的原文 → 摘要与状态快照 → 被移出部分的索引（可按关键词检索）。三层覆盖"刚才说的""聊过什么""当时细节"。

### 4.5 并发

锁的粒度等于隔离的粒度：按 `session_id` 分锁，同会话串行、跨会话并行。锁放在会话存储上，不放在运行时实例上。

### 4.6 异常

能让模型自己纠正的错误（工具不存在、参数不合法、执行失败）统一转成一条观察回注；只有模型接口不可用才终止本轮。

## 五、验收标准

做完的标准不是"能跑通一次"，而是下面这些都能验证：

| # | 验收项 | 判定方式 |
|---|---|---|
| 1 | 4 步循环成立，模型不需要工具时一次调用就结束 | 离线用例：直接回答 / 单工具后再回答 |
| 2 | 模型能基于 schema 自主选工具，参数由模型填 | 断言请求里带了 `tools`；断言工具收到模型给的参数 |
| 3 | 工具结果以 `role=tool` + 配对 id 回注，结构不破 | 贯穿断言遍历消息检查配对 |
| 4 | 两个窗口互不可见（历史、待办、摘要） | 两个会话各记一条待办，互相查不到 |
| 5 | 重启进程后能接着聊 | 写盘 → 新建 store 实例 → 读回历史 |
| 6 | 追问（纯对话 / 带工具）能定位到之前的对象 | 真实 API：把"第二条待办标记完成"跑通 |
| 7 | 长对话触发压缩且不破协议 | 6 轮 + 小预算；压缩后仍能答出旧信息 |
| 8 | 压缩掉的内容还能查回来 | 索引存在 + 模型能检索到被压缩的事实 |
| 9 | 同一会话并发不串台，不同会话能并行 | 并发测试测"同时有几个 run 在调模型"的峰值 |
| 10 | 各类异常都不炸循环 | 未知工具 / 参数非法 / 超时 / 模型 5xx 各有用例 |
| 11 | 每轮能复盘 | trace 里能还原每一步的时间线与耗时 |

**通过门槛**：离线用例全绿（不联网 15 秒内跑完）；真实 API 冒烟通过（证明 payload 被真实服务接受）；上面 11 条逐条有对应用例或探针。

## 六、主要风险

| 风险 | 应对 |
|---|---|
| 模型输出不稳定（半截 JSON、空内容） | 解析层降级 + 把错误当观察回注 |
| 压缩破坏 tool_call 与结果的配对 | 按用户输入切块，块内不动；贯穿断言兜底 |
| 并发写同一份会话 | 按会话加锁，锁覆盖整次 run |
| 上下文撑爆 | 预算 + 三档压缩；被压内容进索引 |
| 说不清"为什么这么设计" | 每个决策配一条实测依据，写进注释与文档 |
